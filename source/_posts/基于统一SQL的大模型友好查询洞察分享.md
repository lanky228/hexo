💡 跨库SQL适配有三条成熟路线（联邦引擎、语义层、引擎统一），没有一条依赖"事后方言转换"。当前"统一SQL+方言转换"方案存在等价函数结构性风险，应向语义层直接生成各库SQL演进。

## 背景

五个子域需要跨 StarRocks/Druid/GaussDB 三个异构数据库查询，AI 需生成一种 SQL 让三库都能执行。当前采用"统一 SQL + 函数映射改写"方案，但已发现 Druid 报文场景查询报错的结构性风险。

业界已有多条成熟路线解决跨库 SQL 适配问题，需对比研判正确的演进方向。

## 当前方案的问题

当前流程：AI 生成统一 SQL（不感知目标库）→ 引擎层函数映射改写 → 分别下推各库执行。

具体表现：

- StarRocks：原生支持该函数，零改写，执行成功
- GaussDB：原生支持该函数，零改写，执行成功
- Druid 报文：FROM_UNIXTIME 函数不下推，内存计算报错
- Druid SQL：改写为等价函数，执行成功（降级路径）

核心问题是：生成统一 SQL 后再改写，某库不支持等价函数即失败。方案依赖每个数据库都存在等价函数可映射，新增不支持等价函数的库就失效。

这不是一个偶然的bug，而是方案的结构性缺陷——把"感知目标库"这个该在生成阶段做的事，推迟到了改写阶段。

## 业界三种路线

### 路线一：联邦引擎——不推 SQL 给源库

Trino 收到查询请求后，不推 SQL 给源库，而是从各库拉取数据到引擎层统一执行 JOIN 和聚合。

为什么不依赖等价函数：SQL 不在源库执行，源库只需吐数据，不需要支持任何特定函数。

代表实践：Meta 日处理数千万查询、EB 级数据；Uber 15 集群、5000+ 节点、日 50 万查询。

### 路线二：语义层——定义指标一次，感知目标库自动生成

语义层定义指标（如"CPU 均值 = 按月聚合 CPU 平均值"），感知目标库，自动生成各库专属 SQL。

- StarRocks → 生成 StarRocks 方言 SQL → 执行
- Druid → 生成 Druid 方言 SQL → 执行
- GaussDB → 生成 GaussDB 方言 SQL → 执行

为什么不依赖等价函数：每个库拿到的是语义层为自己专属生成的 SQL，不存在"映射不了"的问题。

对大模型的友好性：AI 只需声明查什么指标，语义层自动完成方言适配，降低 AI 生成 SQL 的复杂度。

代表实践：dbt MetricFlow、Cube、Netflix DataJunction、Airbnb Minerva。局限：指标建模投入较大（中型企业数百指标 = 数月建模）。

### 路线三：引擎统一——只用一个引擎

AI 生成 SQL（只有一种方言，因为只有一个引擎），统一引擎直接执行。

为什么不依赖等价函数：只有一个引擎、一种方言，不存在跨库映射。

代表实践：Meta 四引擎收敛到 Presto 一个，节省"数十万行代码和数千台机器"；滴滴四引擎收敛到 StarRocks，查询性能 4 倍、总成本降 80%。

关键教训：性能问题可以用工程手段解决，但运维复杂度无法用工程手段消除——这是引擎统一的根本驱动力。局限：迁移成本高，已有异构库存量场景不适用。

## 三种路线对比与选型

| 维度 | 联邦引擎 | 语义层 | 引擎统一 | 当前方案 |
|------|---------|--------|---------|---------|
| 适配方式 | 不推SQL给源库 | 感知目标库直接生成 | 单引擎无跨库 | 统一SQL+运行时改写 |
| 依赖源库SQL能力 | 否 | 否 | 否 | 是 |
| 等价函数依赖风险 | 无 | 无 | 无 | 有（已失败） |
| 跨源JOIN | 支持 | 不支持 | 不适用 | 不支持 |

| 维度 | 联邦引擎 | 语义层 | 引擎统一 | 当前方案 |
|------|---------|--------|---------|---------|
| SQL下推执行 | 否 | 是 | 不适用 | 是 |
| 迁移成本 | 中 | 中 | 高 | 低 |
| 适用本系统 | 不适合 | 最适合 | 不适合 | 有风险 |

### 选型结论

联邦引擎不采用。查询以单数据源为主，不需要跨源 JOIN；联邦引擎拉取数据到引擎层执行，单数据源查询比原生更慢；需额外部署维护 Trino 集群。

引擎统一不采用。三库功能互补（StarRocks 高性能 OLAP、Druid 时序实时、GaussDB 关系型配置），单一引擎无法同时最优；迁移三个生产库业务中断风险大。

语义层采用。三库不动迁移成本最低；感知目标库直接生成该库 SQL，消除等价函数依赖；可与当前方言翻译并行运行，平滑过渡。

## 方言翻译的结构性风险

当前方案分三步，三个风险均发生在第二步（引擎层函数映射改写）：

- Step 1：AI 生成统一 SQL（不感知目标库）
- Step 2：引擎层函数映射改写 ← 三个风险均在此
- Step 3：改写后的 SQL 下推各库执行

风险一，等价函数依赖：每个库必须存在等价函数可替换，否则改写失败。已发生：Druid 报文无等价函数下推，场景失败。

风险二，语义差异不可处理：仅能做函数名替换，无法处理 NULL 聚合行为、时区默认值、时间精度等语义级差异。

风险三，维护负担：每个新函数 × 每个新数据库需新增一条映射规则。5 个函数 × 4 个数据源 = 20 条规则，新增 1 个库则变为 25 条。

当前 SQL 方言转换器基于 Apache Calcite 框架实现函数映射。Druid 报文场景失败已验证风险一，风险二三尚未触发但属结构性隐患。

## 目标架构

核心变化：从"不感知底层 → 统一生成 → 事后改写"到"感知底层 → 直接生成该库 SQL"。

感知机制：语义层维护表-数据库路由映射（metrics 表 → StarRocks、alerts 表 → Druid）。AI 声明指标后，语义层追溯到底层表，查路由映射确定目标库，直接生成该库 SQL。

业界验证：Netflix、Airbnb、Spotify 均已落地。OSI Initiative 40+ 公司参与，语义层正成为产业标准。

## 这个洞察对其他项目的意义

这个选型结论不只适用于我们的系统。任何需要跨异构数据库查询的项目，都会面对同样的分叉：

如果你只有一个数据库，引擎统一是最优解——消除方言问题，运维最简。

如果你需要跨源 JOIN，联邦引擎是唯一选择——牺牲单数据源性能换取跨源能力。

如果你有多个功能互补的数据库但不需跨源 JOIN，语义层是最优解——三库不动、感知目标库直接生成，从根源消除"改不动"的风险。

关键判断标准：问自己"SQL 是在源库执行还是在引擎层执行"。如果源库执行，就必须感知目标库的方言能力——推迟到运行时改写，就是结构性风险的根源。

## ✅ 总结

- 当前"统一 SQL + 方言转换"方案存在结构性风险：依赖各库存在等价函数，Druid 报文场景失败已验证此风险
- 业界三种路线（联邦引擎、语义层、引擎统一）均不依赖事后 SQL 方言转换
- 应向语义层感知底层数据库直接生成各库 SQL 演进：三库不动、迁移成本最低，从根源消除"改不动"的风险
- 选型标准：单库选引擎统一，跨源JOIN选联邦引擎，多库互补选语义层
- 关键判断：SQL 在源库执行就必须感知目标库方言——推迟到运行时改写就是结构性风险
