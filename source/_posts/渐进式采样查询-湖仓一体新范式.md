💡 未来数据库的默认行为应该是先采样给模糊答案，再按需精确。像渐进式图片加载，先模糊后清晰，用户在毫秒内获得方向性判断，再决定是否值得等待精确结果。

## 核心问题：精确优先范式已经走到尽头

### 传统范式的致命假设

传统数据库有一个隐含假设：用户需要精确答案，系统必须扫描全量数据。

数据量小的时候没问题。但从GB到TB到PB，这个假设变成了诅咒：

| 数据量 | 全表扫描延迟 | 用户真正需要 |
|--------|-------------|-------------|
| 1GB | 100ms | 精确答案 |
| 100GB | 10秒 | 可能精确，可能近似就够 |
| 10TB | 17分钟 | 99%的场景近似就够 |
| 1PB | 28小时 | 绝大多数分析只要近似 |

绝大多数分析查询不需要精确答案。

业务方问"上个月GMV是多少"，他要的是"大概3亿还是5亿"的方向性判断，不是"324,782,191.37"的精确数字。传统数据库为了给出精确数字，要扫描几十GB数据，等待几十秒。

### 缓存、物化视图、预聚合为什么不够

| 方案 | 问题 |
|------|------|
| 缓存 | 命中率天花板、数据新鲜度问题 |
| 物化视图 | 预定义维度有限、无法覆盖即席查询 |
| 预聚合 | 丢失细节、维度爆炸、只能回答预设问题 |
| Cube/OLAP | 建模重、维度组合爆炸 |

这些方案都是"提前算好"的思路。但即席查询的组合是无限的，预计算永远追不上需求。需要一种新范式：不预计算答案，而是减少计算量。

## 新范式：渐进式采样查询

### 核心理念

借鉴渐进式图片加载（Progressive Image Loading）：

```
传统： ████████████████████████████ → 30秒后一次性返回精确结果
渐进： ██░░░░░░░░░░░░░░░░░░░░░░░░░ → 50ms返回±5%近似结果
      ████████████████████████████ → 30秒返回精确结果（按需）
```

用户在50毫秒内就能看到"大概3亿"，然后自己决定是否等2秒看"3.05亿"，还是直接用3亿做决策。

### 三阶段执行模型

阶段一：采样快查（Sample Scan）

```sql
-- 用户写的是普通SQL
SELECT region, SUM(amount) FROM orders 
WHERE date > '2026-01-01' 
GROUP BY region;
```

系统内部自动执行：

```sql
-- 引擎自动改写：1%采样 + 误差估算
SELECT region, SUM(amount) * 100 as estimated_sum
FROM orders TABLESAMPLE(1%) 
WHERE date > '2026-01-01'
GROUP BY region;
-- 结果：华东≈2.8亿(±5%) 华南≈1.5亿(±5%)
```

用户无感知。他写的是普通SQL，系统自动选择采样策略，返回结果时附带置信区间。

阶段二：精度提升（Refine）。如果用户需要更精确的结果，系统自动扩展到10%采样，误差降到±1.5%，耗时2.3秒。

阶段三：精确扫描（Exact）。只有用户明确要求精确结果时才全量扫描，耗时28秒。

### 查询意图自动识别

系统根据SQL模式自动判断走哪条路径：

| 查询模式 | 默认路径 | 示例 |
|----------|---------|------|
| SUM/AVG/COUNT + GROUP BY | 采样快查 | 各地区GMV |
| SELECT * WHERE id = ? | 索引直查 | 查某订单详情 |
| SELECT * WHERE ... | 采样 + 翻页 | 看几条样本数据 |
| JOIN + GROUP BY | 双侧采样 | 关联用户和订单分析 |

### 明细查询的采样范式

用户说"我要看华东地区的大额订单"，传统方式要扫描全表过滤。新范式分三步：

第一步：采样返回20条样本（50ms），用户看到数据分布。第二步：用户基于样本缩小范围，只要金额>10万的。第三步：精确扫描缩小后的范围，从1亿行缩小到几百条，扫描成本微不足道。

采样不是替代精确查询，而是帮助用户快速缩小精确查询的范围。采样让搜索空间从1亿行指数级缩小到几千行，然后精确查询成本就微不足道了。

## 技术实现：表格式内建采样

### Iceberg表格式扩展

采样应该内建到表格式中，让采样成为表的一等公民。Iceberg 的 `SamplingSpec` 属性应维护多级采样（0.1%/1%/5%/10%），每级记录采样率、方法、采样子集文件与统计信息。

采样方法分五类：系统采样（按文件块随机）、伯努利（按行）、分层（按分组列）、蓄水池（流式）、索引采样（基于索引列）。

### 自描述采样

表格式 manifest 自带采样元数据：每个采样级别记录采样率、采样子集文件列表、行数、置信度、刷新策略。任何支持 Iceberg 的引擎（Trino、Spark、Flink、DuckDB）都能透明读取采样数据，零额外配置。

### 增量采样维护

数据写入时触发增量采样：1% 池每 100 行取 1 行，5% 池每 20 行取 1 行，10% 池每 10 行取 1 行。采样数据与主数据秒级同步。

不是维护独立的采样表，而是通过文件级别的元数据标记实现。主数据文件中哪些 block 属于哪个采样级别，查询时直接选择对应 block 读取。

### Zone Maps + 采样的协同

采样和 Zone Maps 天然互补。Zone Maps 过滤后剩余 10% 文件，再 1% 采样后实际扫描全表的 0.01%。Zone Maps 减少 90%，采样再减少 99%，总体减少 99.9% 的 I/O。

Zone Maps 减少一个数量级，采样再减少两个数量级，三次叠加后 1PB 数据变成 1GB 扫描量。

## 大一统：湖仓一体的破局点

### 当前数据架构的三难困境

当前三类方案各自为政：HTAP（事务分析一体）、湖仓一体（结构化+半结构化统一）、数据湖联邦（多源跨平台统一）。用户要跨 TP 数据库、数据湖、外部数据源做分析，传统方案要么联邦查询（Trino/Presto 能跨源但全量扫描慢），要么数据搬运（ETL 延迟大成本高），要么数据共享（Iceberg/Delta 只解决湖内共享，不解决 TP 和湖之间的鸿沟）。

### 采样范式为什么能统一三层

因为采样归一化了不同数据源的查询速度：

| 数据源 | 全量扫描 | 1%采样扫描 |
|--------|---------|-----------|
| TP行存（NVMe） | 10秒 | 0.1秒 |
| AP列存（SSD） | 30秒 | 0.3秒 |
| 数据湖（S3/OSS） | 5分钟 | 3秒 |
| 外部JDBC（MySQL） | 10分钟 | 6秒 |

全量扫描时，TP和S3的速度差30倍，用户体验割裂。但1%采样后，TP是0.1秒，S3是3秒，都在可接受范围内。

### 统一查询接口

用户写一条标准 SQL 透明跨源：TP 行存（热）、数据湖 Iceberg（温）、外部 JDBC（冷）三源 JOIN，系统内部走三阶段渐进采样。

联邦查询的瓶颈永远是最慢的数据源。全量扫描时 S3/JDBC 拖慢整体；采样后各源速度差缩小，联邦查询变得可行。

### 外部数据目录兼容

采样范式的另一个优势是外部数据源不需要改表格式就能受益。Iceberg原生表格式数据达到最优，因为采样元数据内建在表中，引擎可以直接定位采样文件。外部数据源通过适配层实现采样，性能稍逊但仍然可用。

## 采样质量控制

### 误差保证

不是随机采样就完事，必须给出统计保证。基于置信区间公式（点估计 ± Z × σ/√n，Z=1.96 对应 95% 置信度），1% 采样 100 万行得到 1 万样本时，SUM 聚合误差通常 < 0.001%。

系统自动返回精度元数据：结果值、置信度、各分组误差范围、采样量、执行耗时、是否可提升精度。

### 自适应采样率

不同查询需要不同采样率。误差容忍 5% 用 1% 采样（快），1% 用 5% 采样（中速），0.1% 用 20% 采样（较慢），精确则全量扫描。决策因素包括数据分布方差、查询复杂度、用户误差容忍度、时间预算。

### 分层采样处理数据倾斜

数据不均匀时简单随机采样效果差。小分组可能样本极少导致误差爆炸。分层采样按分组列分层后各层独立采样，并对小分组保底至少 100 行，保证各层误差均匀。

## 用户无感上车策略

### 为什么无感是成功的关键

技术再好，如果要求用户改SQL、改应用、学新语法，大概率推不动。采样范式要成功，必须零改动上车。

### 四层无感设计

SQL 零改动：用户写标准 SQL，引擎内部自动改写为 `TABLESAMPLE(1%)` 并对聚合结果乘以采样倍率。

结果自动标注：返回结果自动附带精度信息（如"华东 ≈2.8亿 ±5%"），但不打断使用流程。

BI 工具适配：Tableau/Superset/Metabase 通过标准 JDBC 连接，采样结果自动呈现。JDBC 驱动在返回结果的同时返回精度元数据。

表格式自描述：Iceberg 表创建时自动启用采样，数据写入时自动维护多级采样、Zone Maps、采样统计信息。

### 渐进式上车路径

阶段一：引擎层自动采样，升级 Trino/StarRocks/Calcite 即可获得 2-10 倍加速，零改动。

阶段二：Iceberg 采样元数据增强，新建表自动内建，旧表 ALTER 升级。

阶段三：生态集成，JDBC 暴露精度元数据、BI 展示置信区间。

阶段四：AI 驱动，预测最佳采样率、自动分层策略、查询模式学习。

## 对比分析：为什么采样范式最可能成功

### vs 现有方案

现有方案的核心思路和通用性对比：

| 方案 | 核心思路 | 通用性 |
|------|---------|--------|
| 缓存 | 重用历史结果 | 低（只对重复查询） |
| 物化视图 | 预计算 | 低（预设维度） |
| Cube/OLAP | 多维预聚合 | 低（需建模） |
| BlinkDB | 近似查询 | 中（独立系统） |
| 渐进式采样 | 默认采样+按需精确 | 高（任何查询） |

上手成本和兼容性对比：

| 方案 | 上手成本 | 外部数据兼容 |
|------|---------|------------|
| 缓存 | 中 | 不兼容 |
| 物化视图 | 高 | 不兼容 |
| Cube/OLAP | 高 | 不兼容 |
| BlinkDB | 高 | 不兼容 |
| 渐进式采样 | 零（无感上车） | 兼容 |

### 成功的四个必要条件

零改动上车：表格式自描述 + 引擎自动改写。误差可控：置信区间 + 自适应采样率。全场景覆盖：分层采样 + 双侧JOIN采样。跨源统一：采样归一化不同数据源速度。

### 与现有技术的融合点

采样范式不是推翻现有技术，而是在其上增加一层：渐进式采样查询层叠加在已有的查询优化器、执行引擎、表格式层、存储层之上。每一层都保留已有技术，采样层是新增的。Calcite 可扩展为采样感知优化器，Trino 可增加采样路由器，Iceberg 可扩展采样元数据，向量化执行照常工作只是处理的数据量少了 99%。

## 技术挑战与解法

### JOIN场景的采样

JOIN 是最难采样的。两表各自采样 1%，JOIN 结果可能只有 0.01% 的行，误差爆炸。

三种解法：大表采样 + 小表全量（orders 1% + users 全量，误差可控）；基于 JOIN 键的分层采样（两表按相同键分层，保证 JOIN 完整性）；图采样（将多表 JOIN 建模为图，随机游走采样保证代表性）。

### COUNT DISTINCT

`COUNT(DISTINCT user_id)` 对采样极其敏感，去重计数无法简单按采样率线性放大。

解法：HyperLogLog + 采样。HLL 只需固定内存（通常 16KB），1% 采样 100 万行用 HLL 估算误差约 5%，80ms 返回。对比全量扫描去重 28 秒。

### 数据分布变化

数据分布突变（如某天突然多了 10 倍数据）会让旧采样统计失准。

解法：自适应采样校准。写入时监控分布变化，超阈值触发采样池重建；查询时与 Zone Map 统计交叉对比，偏差大则自动升级采样率。

### 用户信任

用户可能不信任"模糊"结果，尤其是中国企业数据文化偏向精确。

解法分三阶段：第一阶段采样与精确并行展示，让用户看到误差通常 < 5%；第二阶段采样默认展示、精确可选；第三阶段采样成为默认范式，精确查询只用于财务对账等场景。

## 未来演进路线

近期（1-2年）：Trino/StarRocks 增加自动采样路由，Iceberg 扩展采样元数据属性，JDBC 驱动暴露置信区间元数据，开源参考实现（基于 Calcite）。

中期（3-5年）：Iceberg/Paimon/Hudi 原生支持采样元数据，Apache 社区推动采样查询标准，BI 工具原生支持渐进式结果展示。

远期（5-10年）：AI 预测查询最佳采样率，自适应采样策略，查询模式学习，采样质量持续优化。

## 这对读者意味着什么

如果你是数据平台负责人或架构师，这篇文章传递的核心信号是：查询引擎的下一个竞争维度不是"谁扫描得更快"，而是"谁需要扫描得更少"。渐进式采样范式把统计学引入了查询执行路径，这改变了性能优化的底层逻辑。传统优化手段（向量化、CBO、缓存）都在优化"怎么扫得更快"，采样范式解决的是"要不要扫这么多"。

对实践者来说，可以关注三个方向。第一，评估现有查询负载中有多少是探索性分析、趋势判断、仪表盘这类近似可接受的场景，这些是采样范式的首批受益者。第二，关注 Iceberg 社区在采样元数据方面的进展，表格式内建采样是这个范式落地的关键基础设施。第三，在引擎选型时，把"是否支持自动采样路由"纳入评估维度，这会越来越重要。

从数据平台演进的大图景看，采样范式可能成为湖仓一体真正落地的催化剂。当前湖仓一体的核心痛点是对象存储延迟高，联邦查询被最慢的数据源拖累。采样归一化了不同数据源的速度差，让跨源查询变得可行。如果这个范式成立，数据平台的架构会从"搬运数据到计算"转向"采样数据到决策"。

## 常见问题

Q: 采样查询会不会给出错误答案？

采样查询提供的是近似结果，不是错误结果。关键是置信区间可控，0.1% 采样在大多数聚合查询上误差不超过 5%。用户根据近似结果决定是否值得等待全量扫描。

Q: 为什么不直接用缓存或物化视图？

缓存和物化视图是预计算思路，问题是查询组合爆炸、维度变更失效、新鲜数据查不到。渐进式采样是算得快但模糊的思路，不预存任何结果，对所有查询即时响应。

Q: 渐进式采样查询需要改用户的 SQL 吗？

不需要。表格式内建采样能力，引擎在执行层自动插入采样算子。用户写普通 SQL，引擎根据查询类型自动决定采样策略。

Q: 采样查询适合所有场景吗？

不适合。需要精确结果的场景（金融对账、合规审计、计数查询）仍然需要全量扫描。采样适合探索性分析、趋势判断、仪表盘、A/B 实验方向性判断，这些场景占分析查询的 80% 以上。

## ✅ 总结

渐进式采样查询范式的核心命题：扫描采样数据给近似答案，快且够准，按需精确。这个范式能统一湖仓一体的根本原因：

- 速度归一化：采样让不同数据源的查询速度差异从30倍降到3倍，用户体验统一
- 零改动上车：表格式自描述采样，SQL不需要改，用户无感
- 误差可控：置信区间让用户知道结果的可靠程度
- 渐进精化：先模糊后精确，搜索空间指数级缩小后再全量扫描
- 全场景覆盖：聚合走采样、明细先采样定位、JOIN用相关性采样、点查走索引

它满足成功的四个必要条件：零改动、误差可控、全场景、跨源统一。缓存、物化视图、Cube 等方案都在这四个条件中有短板。采样范式不是替代现有技术，而是在其上增加一个智能降速层，让所有现有引擎和表格式都能受益。

最终愿景：让大数据在查询时自动变成小数据。不是靠缓存，不是靠预计算，而是靠统计学的力量。100倍数据量只需要扫描1%，这就是采样的数学之美。
