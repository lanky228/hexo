💡 一句话总结：未来数据库的默认行为不应该是"扫描所有数据给精确答案"，而应该是"先采样给模糊答案，再按需精确"——这像渐进式图片加载一样，先模糊后清晰，让用户在毫秒内获得方向性判断，再决定是否值得等待精确结果。

## 核心问题：为什么精确优先的范式已经走到尽头

### 传统范式的致命假设

传统数据库有一个隐含假设：**用户需要精确答案，系统必须扫描全量数据。**

这个假设在数据量小的时候没问题。但当数据量从GB到TB到PB时，这个假设变成了诅咒：

| 数据量 | 全表扫描延迟 | 用户真正需要 |
|--------|-------------|-------------|
| 1GB | 100ms | 精确答案 |
| 100GB | 10秒 | 可能精确，可能近似就够 |
| 10TB | 17分钟 | 99%的场景近似就够 |
| 1PB | 28小时 | 绝大多数分析只要近似 |

**现实是：绝大多数分析查询不需要精确答案。**

业务方问"上个月GMV是多少"，他要的是"大概3亿还是5亿"的方向性判断，不是"324,782,191.37"的精确数字。但传统数据库为了给出精确数字，要扫描几十GB数据，等待几十秒。

### 缓存、物化视图、预聚合为什么不够

| 方案 | 问题 |
|------|------|
| 缓存 | 命中率天花板、数据新鲜度问题、缓存失效成本 |
| 物化视图 | 预定义维度有限、无法覆盖即席查询、维护成本高 |
| 预聚合 | 丢失细节、维度爆炸、只能回答预设问题 |
| Cube/OLAP | 建模重、维度组合爆炸、对新数据源适应性差 |

这些方案都是"提前算好"的思路——预计算所有可能答案。但即席查询的组合是无限的，预计算永远追不上需求。

**需要一种新的范式：不预计算答案，而是减少计算量。**

## 新范式：渐进式采样查询（Progressive Sampling Query）

### 核心理念

借鉴渐进式图片加载（Progressive Image Loading）：

```
传统： ████████████████████████████ → 30秒后一次性返回精确结果
渐进： ██░░░░░░░░░░░░░░░░░░░░░░░░░ → 50ms返回±5%近似结果
       ████░░░░░░░░░░░░░░░░░░░░░░ → 2秒返回±1%近似结果
       ████████████████████████████ → 30秒返回精确结果（按需）
```

用户在50毫秒内就能看到"大概3亿"，然后自己决定是否等2秒看"3.05亿"，还是直接用3亿做决策。

### 三阶段执行模型

**阶段一：采样快查（Sample Scan）**

```sql
-- 用户写的是普通SQL
SELECT region, SUM(amount) FROM orders 
WHERE date > '2026-01-01' 
GROUP BY region;
```

系统内部自动执行：
```sql
-- 引擎自动改写：1%采样 + 误差估算
SELECT region, SUM(amount) * 100 as estimated_sum
FROM orders TABLESAMPLE(1%) 
WHERE date > '2026-01-01'
GROUP BY region;
-- 结果：华东≈2.8亿(±5%) 华南≈1.5亿(±5%) 华北≈0.9亿(±5%)
-- 耗时：80ms
```

关键：**用户无感知**。他写的是普通SQL，系统自动选择采样策略，返回结果时附带置信区间。

**阶段二：精度提升（Refine）**

如果用户需要更精确的结果（点击"提升精度"或系统判断查询意图需要更高精度）：

```sql
-- 自动扩展到10%采样
SELECT region, SUM(amount) * 10 as estimated_sum
FROM orders TABLESAMPLE(10%)
WHERE date > '2026-01-01'
GROUP BY region;
-- 结果：华东≈3.02亿(±1.5%) 华南≈1.48亿(±1.5%) 华北≈0.91亿(±1.5%)
-- 耗时：2.3秒
```

**阶段三：精确扫描（Exact）**

只有用户明确要求精确结果时才全量扫描：

```sql
-- 用户显式请求：EXACT MODE
SELECT region, SUM(amount) FROM orders
WHERE date > '2026-01-01'
GROUP BY region EXACT;
-- 结果：华东=301,982,473 华南=148,237,891 华北=91,043,567
-- 耗时：28秒
```

### 查询意图自动识别

系统根据SQL模式自动判断走哪条路径：

| 查询模式 | 意图判断 | 默认路径 | 示例 |
|----------|---------|---------|------|
| SUM/AVG/COUNT + GROUP BY | 汇总分析 | 采样快查 | 各地区GMV |
| SUM + ORDER BY + LIMIT | TopN | 采样快查 | 销量前10城市 |
| COUNT(*) | 总量估算 | 采样快查 | 总用户数 |
| SELECT * WHERE id = ? | 精确点查 | 索引直查（不走采样） | 查某订单详情 |
| SELECT * WHERE ... | 明细浏览 | 采样 + 翻页提示 | 看几条样本数据 |
| JOIN + GROUP BY | 关联分析 | 采样快查（双侧采样） | 关联用户和订单分析 |

### 明细查询的采样范式

用户说"我要看华东地区的大额订单"——这本质上是明细查询，传统方式要扫描全表过滤。新范式：

```
第一步：采样返回20条样本（50ms）
  → 用户看到数据分布：金额范围、时间分布、商品类别
  
第二步：用户基于样本缩小范围
  → "我只要金额>10万的，按时间倒序"
  
第三步：精确扫描（缩小后的范围）
  → 范围已经从"华东所有订单"缩小到"华东>10万"的几百条
  → 精确扫描只需扫描1000行而非1亿行
```

**关键洞察：采样不是替代精确查询，而是帮助用户快速缩小精确查询的范围。** 这就是"指数下降后再精确获取"的精髓——采样让搜索空间从1亿行指数级缩小到几千行，然后精确查询成本就微不足道了。

## 技术实现：表格式内建采样

### Iceberg表格式扩展

采样不应该是外挂式的，而应该内建到表格式中——让采样成为表的一等公民：

```java
// Iceberg Table Properties 扩展
public class SamplingSpec {
    // 采样级别：系统自动维护多级采样
    private Map<Double, SamplingLevel> levels;  // 0.1%, 1%, 5%, 10%
    
    // 每个级别的实现方式
    class SamplingLevel {
        double percentage;           // 采样率
        SamplingMethod method;       // 采样方法
        FileGroup sampleFiles;       // 采样子集文件
        Statistics statistics;       // 采样统计信息
        long lastRefreshTime;        // 最后刷新时间
    }
    
    // 采样方法
    enum SamplingMethod {
        SYSTEM,        // 系统采样（按文件块随机选取）
        BERNOULLI,     // 伯努利采样（按行随机选取）
        STRATIFIED,    // 分层采样（按分组列分层）
        RESERVOIR,     // 蓄水池采样（流式数据）
        INDEXED        // 索引采样（基于索引列选取）
    }
}
```

### 自描述采样（Self-Describing Sampling）

表格式自带采样元数据，任何引擎都能读取：

```json
// Iceberg manifest 中的采样描述
{
  "table": "orders",
  "sampling": {
    "levels": [
      {"rate": 0.01, "files": ["file_001.parquet", "file_042.parquet", ...], "rows": 100000},
      {"rate": 0.05, "files": ["file_001.parquet", ...], "rows": 500000},
      {"rate": 0.10, "files": ["file_001.parquet", ...], "rows": 1000000}
    ],
    "method": "system",
    "confidence": 0.95,
    "auto_refresh": true,
    "refresh_strategy": "incremental"
  }
}
```

**关键优势**：任何支持Iceberg的引擎（Trino、Spark、Flink、DuckDB）都能透明地使用采样数据，不需要额外配置。

### 增量采样维护

数据写入时自动维护采样：

```
新数据写入 → 触发增量采样
  ├── 1%采样池：每100行取1行（概率采样）
  ├── 5%采样池：每20行取1行
  └── 10%采样池：每10行取1行

效果：采样数据与主数据秒级同步，不是独立的第二份数据
```

这不是维护独立的采样表，而是通过**文件级别的元数据标记**实现——主数据文件中哪些block属于哪个采样级别，查询时直接选择对应block读取。

### Zone Maps + 采样的协同

采样和Zone Maps是天然互补的：

```
全表：100个文件，每个文件1000个block
  → Zone Maps过滤后：剩余10个文件，每个100个block = 1000个block
  
采样1%：
  → 从1000个block中取10个block = 10个block
  → 实际扫描：全表的 0.01%
  
效果：Zone Maps 90% + 采样 99% = 总体减少 99.9% 的I/O
```

**这就是"让大数据变成小数据"的数学证明——Zone Maps减少一个数量级，采样再减少两个数量级，三次叠加后1PB数据变成1GB扫描量。**

## 大一统：库仓湖一体的破局点

### 当前数据架构的三难困境

```
     库仓一体(HTAP)          湖仓一体(Lakehouse)        数据湖联邦(Federation)
     TP + AP 统一             结构化 + 半结构化统一       多源跨平台统一
     ↑                        ↑                        ↑
     |    各自为政，互不兼容，查询体验割裂              |
```

用户要跨TP数据库、数据湖、外部数据源做分析？传统方案：
- 联邦查询（Trino/Presto）：能跨源但速度慢（全量扫描远程数据源）
- 数据搬运（ETL）：延迟大、成本高
- 数据共享（Iceberg/Delta）：只解决湖内共享，不解决TP和湖之间的鸿沟

### 采样范式为什么能统一三层

**因为采样归一化了不同数据源的查询速度：**

| 数据源 | 全量扫描 | 1%采样扫描 | 速度差异 |
|--------|---------|-----------|---------|
| TP行存（NVMe） | 10秒 | 0.1秒 | 100x |
| AP列存（SSD） | 30秒 | 0.3秒 | 100x |
| 数据湖（S3/OSS） | 5分钟 | 3秒 | 100x |
| 外部JDBC（MySQL） | 10分钟 | 6秒 | 100x |

全量扫描时，TP和S3的速度差30倍——用户体验割裂。但1%采样后，TP是0.1秒，S3是3秒——**都在"可接受"范围内，用户体验统一。**

### 统一查询接口

```sql
-- 用户写一条SQL，透明跨源
SELECT 
  o.region,
  SUM(o.amount) as gmv,
  AVG(u.age) as avg_age,
  COUNT(DISTINCT u.user_id) as users
FROM mysql.orders o           -- TP行存（热数据）
JOIN lake.user_profile u       -- 数据湖Iceberg（温数据）  
  ON o.user_id = u.user_id
JOIN ext_crm.customer_tags c   -- 外部JDBC（冷数据）
  ON u.user_id = c.user_id
WHERE o.date > '2026-01-01'
GROUP BY o.region;
```

系统内部执行计划：

```
阶段一（50ms-3s）：全局采样
  ├── mysql.orders: 1%采样（0.1s）→ gmv≈3亿(±5%)
  ├── lake.user_profile: 1%采样（0.3s）→ avg_age≈28(±3%)
  ├── ext_crm.customer_tags: 1%采样（6s）→ users≈50万(±5%)
  └── JOIN在采样集上执行（小数据量快速JOIN）

阶段二（3-30s）：精度提升
  ├── 扩大到5%采样
  └── 误差降到±1.5%

阶段三（30s+）：精确扫描（按需）
  ├── 全量JOIN
  └── 精确结果
```

**关键：联邦查询的瓶颈永远是最慢的数据源。全量扫描时S3/JDBC拖慢整体；采样后各源速度差缩小，联邦查询变得可行。**

### 外部数据目录兼容

采样范式的另一个优势——**外部数据源不需要改表格式就能受益**：

| 数据源类型 | 采样实现方式 | 用户感知 |
|-----------|------------|---------|
| Iceberg原生表 | 内建采样元数据，零开销 | 最优体验 |
| Parquet/ORC文件 | 文件级系统采样（随机选文件） | 接近最优 |
| Hive表 | 文件级采样 + Hive统计信息辅助 | 良好 |
| JDBC数据源 | `TABLESAMPLE`透传或应用层采样 | 可用 |
| API/REST数据源 | 应用层采样 + 缓存 | 基本可用 |

**Iceberg原生表格式数据达到最优**——因为采样元数据内建在表中，引擎可以直接定位采样文件，零额外开销。外部数据源通过适配层实现采样，性能稍逊但仍然可用。

## 采样质量控制

### 误差保证

不是随机采样就完事——必须给出统计保证：

```
置信区间 = 点估计 ± Z * (σ / √n)

Z = 1.96（95%置信度）
σ = 样本标准差
n = 样本量

示例：
  1%采样，100万行 → 样本1万行
  SUM(amount) = 3,000,000
  σ = 500
  置信区间 = 3,000,000 ± 1.96 * (500/√10000) = 3,000,000 ± 9.8
  误差 < 0.001%
```

系统自动计算并展示：

```json
{
  "result": {"华东": 280000000, "华南": 150000000, "华北": 90000000},
  "confidence": 0.95,
  "error_margin": {"华东": "±5.2%", "华南": "±4.8%", "华北": "±6.1%"},
  "sample_size": 10000,
  "execution_time": "80ms",
  "full_scan_estimated_time": "28s",
  "refine_available": true
}
```

### 自适应采样率

不同查询需要不同采样率——系统自动选择：

```
目标误差 < 5%  → 1%采样即可（快）
目标误差 < 1%  → 5%采样（中速）
目标误差 < 0.1% → 20%采样（较慢）
目标误差 = 0    → 全量扫描（慢）

决策因素：
  数据分布方差（方差大需要更多样本）
  查询复杂度（JOIN需要双侧采样）
  用户设置（默认误差容忍度）
  时间预算（用户可接受的等待时间）
```

### 分层采样处理数据倾斜

数据不均匀时，简单随机采样效果差。分层采样：

```
orders表按地区分布：
  华东: 60% 数据
  华南: 25% 数据  
  华北: 10% 数据
  西部: 5% 数据

简单随机1%采样：
  西部可能只有50行 → 误差极大

分层采样1%：
  华东取60% * 1% = 0.6%的行
  华南取25% * 1% = 0.25%的行
  华北取10% * 1% = 0.1%的行
  西部取5% * 1% = 0.05%的行（但保底至少100行）
  
  → 各层都有足够样本，误差均匀
```

## 用户无感上车策略

### 为什么"无感"是成功的关键

技术再好，如果要求用户改SQL、改应用、学新语法——大概率推不动。采样范式要成功，必须**零改动上车**。

### 四层无感设计

**第一层：SQL零改动**

```sql
-- 用户写的SQL（完全标准）
SELECT region, SUM(amount) FROM orders GROUP BY region;

-- 引擎内部自动改写（用户看不到）
SELECT region, SUM(amount) * 100 FROM orders TABLESAMPLE(1%) GROUP BY region;
```

**第二层：结果自动标注**

用户看到的结果自动附带精度信息，但不打断使用流程：

```
┌─────────────────────────────────────────┐
│ region    │ SUM(amount)  │ 置信度       │
│───────────┼──────────────┼──────────────│
│ 华东      │ ≈280,000,000 │ ±5% (1%采样) │
│ 华南      │ ≈150,000,000 │ ±5% (1%采样) │
│ 华北      │ ≈90,000,000  │ ±5% (1%采样) │
├─────────────────────────────────────────┤
│ [提升精度] [导出] [可视化]               │
└─────────────────────────────────────────┘
```

**第三层：BI工具适配**

BI工具（Tableau/Superset/Metabase）通过标准JDBC连接，采样结果自动呈现。不需要BI工具做任何适配——JDBC驱动在返回结果的同时返回精度元数据。

**第四层：表格式自描述**

Iceberg表创建时自动启用采样，不需要DBA配置：

```sql
-- 建表语句（完全标准）
CREATE TABLE orders (
  id BIGINT,
  region STRING,
  amount DECIMAL(10,2),
  date DATE
) STORED AS ICEBERG;

-- 系统自动行为：
-- 1. 数据写入时自动维护多级采样
-- 2. Zone Maps自动收集
-- 3. 采样统计信息自动更新
-- 4. 查询时自动使用采样
```

### 渐进式上车路径

```
阶段1（0改动）：引擎层自动采样
  → 只需要升级查询引擎（Trino/StarRocks/Calcite）
  → 对已有Iceberg/Parquet表自动启用文件级采样
  → 用户立即获得2-10倍加速

阶段2（表格式增强）：Iceberg采样元数据
  → 新建表自动内建采样
  → 采样精度提升、开销降低
  → 旧表通过ALTER TABLE升级

阶段3（生态集成）：BI/应用层适配
  → JDBC驱动暴露精度元数据
  → BI工具展示置信区间
  → 应用层实现"渐进式UI"

阶段4（AI驱动）：智能采样选择
  → AI预测最佳采样率
  → 自动分层采样策略
  → 查询模式学习与优化
```

## 对比分析：为什么采样范式最可能成功

### vs 现有方案

| 方案 | 核心思路 | 通用性 | 上手成本 | 外部数据兼容 | 误差可控 |
|------|---------|--------|---------|------------|---------|
| 缓存 | 重用历史结果 | 低（只对重复查询） | 中 | 不兼容 | 无误差但数据旧 |
| 物化视图 | 预计算 | 低（预设维度） | 高 | 不兼容 | 无误差但维度固定 |
| Cube/OLAP | 多维预聚合 | 低（需建模） | 高 | 不兼容 | 无误差但覆盖有限 |
| BlinkDB | 近似查询 | 中（独立系统） | 高 | 不兼容 | 可控 |
| **渐进式采样** | **默认采样+按需精确** | **高（任何查询）** | **零（无感上车）** | **兼容** | **可控** |

### 成功的四个必要条件

1. **零改动上车** — 不需要改SQL、改表结构、改应用代码 → ✓ 表格式自描述 + 引擎自动改写
2. **误差可控** — 用户知道结果的可靠程度 → ✓ 置信区间 + 自适应采样率
3. **全场景覆盖** — 聚合/明细/JOIN都受益 → ✓ 分层采样 + 双侧JOIN采样
4. **跨源统一** — 库仓湖一体兼容 → ✓ 采样归一化不同数据源速度

### 与现有技术的融合点

采样范式不是推翻现有技术，而是在其上增加一层：

```
┌──────────────────────────────────────────────────┐
│        渐进式采样查询层（新范式）                   │
│  意图识别 → 采样路由 → 误差估算 → 渐进精化         │
├──────────────────────────────────────────────────┤
│        查询优化器层（已有）                         │
│  Calcite / Trino / StarRocks 优化器               │
├──────────────────────────────────────────────────┤
│        执行引擎层（已有）                          │
│  向量化执行 / MPP / JIT                           │
├──────────────────────────────────────────────────┤
│        表格式层（增强）                            │
│  Iceberg + 采样元数据 / Parquet + 文件采样         │
├──────────────────────────────────────────────────┤
│        存储层（已有）                              │
│  行存 / 列存 / 对象存储 / PMem                     │
└──────────────────────────────────────────────────┘
```

每一层都保留已有技术，采样层是新增的。这意味着：
- Calcite可以扩展为采样感知的优化器
- Trino可以增加采样路由器
- Iceberg可以扩展采样元数据
- 向量化执行照常工作，只是处理的数据量少了99%

## 技术挑战与解法

### 挑战一：JOIN场景的采样

JOIN是最难采样的——两表JOIN如果各自采样1%，JOIN结果可能只有0.01%的行，误差爆炸。

**解法：相关性感知采样**

```
方案A：大表采样 + 小表全量
  orders(1亿行) 1%采样 → 100万行
  users(10万行) 全量 → 10万行
  JOIN结果：误差可控

方案B：基于JOIN键的分层采样
  两个表都按user_id分层
  相同user_id在两个表中都被选中或都不选
  → 保证JOIN完整性

方案C：图采样（Graph Sampling）
  将多表JOIN建模为图
  在图上做随机游走采样
  保证JOIN结果的代表性
```

### 挑战二：COUNT DISTINCT

`COUNT(DISTINCT user_id)` 是采样最难的场景——去重计数对采样极其敏感。

**解法：HyperLogLog + 采样**

```
传统：COUNT(DISTINCT)需要全量扫描+哈希去重
采样+HLL：
  1%采样 → 用HyperLogLog估算去重基数
  HLL只需要固定内存（通常16KB）
  采样100万行 → HLL估算误差约5%
  
效果：1%采样 + HLL = 80ms返回 ±5% 的去重结果
对比：全量扫描去重 = 28秒返回精确结果
```

### 挑战三：数据分布变化

如果数据分布突变（比如某天突然多了10倍数据），旧的采样统计可能不准。

**解法：自适应采样校准**

```
写入时监控数据分布变化
  → 分布变化超过阈值 → 触发采样池重构建
  → 分布稳定 → 增量更新采样
  
查询时交叉验证
  → 采样结果与Zone Map统计交叉对比
  → 偏差大 → 自动升级到更高采样率
```

### 挑战四：用户信任

用户可能不信任"模糊"结果——尤其是中国企业的数据文化偏向精确。

**解法：渐进式信任建立**

```
第一阶段：采样 + 精确并行展示
  → 展示采样结果（快）和精确结果（慢）的差异
  → 用户看到误差通常 < 5%
  
第二阶段：采样结果默认展示，精确可选
  → 用户逐渐习惯用采样结果做决策
  → 需要精确时点击"验证"

第三阶段：采样成为默认范式
  → 业务决策基于采样结果
  → 精确查询只用于财务对账等场景
```

## ✅ 总结

渐进式采样查询范式的核心命题：

**传统范式：扫描全量数据 → 给精确答案 → 慢但准**
**新范式：扫描采样数据 → 给近似答案 → 快且够准 → 按需精确**

这个范式能统一库仓湖一体的根本原因：

1. **速度归一化** — 采样让不同数据源的查询速度差异从30倍降到3倍，用户体验统一
2. **零改动上车** — 表格式自描述采样，SQL不需要改，用户无感
3. **误差可控** — 置信区间让用户知道结果的可靠程度，不是盲目的模糊
4. **渐进精化** — 先模糊后精确，搜索空间指数级缩小后再全量扫描
5. **全场景覆盖** — 聚合走采样、明细先采样定位、JOIN用相关性采样、点查走索引

**为什么这是最可能成功的技术路线？**

因为它满足了成功的四个必要条件——零改动、误差可控、全场景、跨源统一。而缓存、物化视图、Cube等方案都在这四个条件中有短板。采样范式不是替代现有技术，而是在其上增加一个"智能降速"层，让所有现有引擎和表格式都能受益。

**最终愿景：让"大数据"在查询时自动变成"小数据"——不是靠缓存，不是靠预计算，而是靠统计学的力量。100倍数据量只需要扫描1%，这就是采样的数学之美。**
